# mosidas.dev の機能マップ

このディレクトリには mosidas.dev の利用者から見た振る舞いとそれを実アプリで確かめる操作を機能ごとに書く。操作の前に本書を読む。次に該当する機能ファイルを開く。

## 共通の前提

- [mosidas.dev の検証の手引き](../README.md) の「1. 起動」の手順で起動してある。「2. 健康診断」の 6 項目がすべて ok である。
- 操作するシェルに `RUN_ID` を設定してある。そのシェルで `. "docs/verify/runs/$RUN_ID/run.env"` を実行して `$BASE` と `$EVIDENCE_DIR` を読み込んである。
- コマンドはリポジトリのルートで実行する。
- 制作物・記事・お知らせの一覧は up のビルドが作業ツリーの `src/data/` のファイルから作る。up はお知らせと Zenn の記事を取得しないので画面の一覧は `src/data/` の内容のとおりになる。
- この実行で起動していないインスタンスを操作しない。別の実行のインスタンスはその実行の証拠と状態を持つ。

## 操作の約束

- 機能ファイルの `前提:` に別の指定が無ければ各手順を共通の前提の状態から始める。
- ブラウザーの操作は `docs/verify/scripts/drive.mjs browser "$RUN_ID"` の後に操作を並べて書く。browser は呼び出しのたびに新しい Chrome を起動するので各呼び出しを `open` から始める。
- 機能ファイルに書いた `text` と `shot` の保存先(`shell/before.png` など)は `$EVIDENCE_DIR` からの相対パスである。
- セレクターは id・role・aria の属性・data 属性・リンク先と送信先のパス(`href` とフォームの `action` の値)・要素の名前(`h1`・`main`・`nav`・`a`・`form`・`button`)で書く。class の名前と DOM の位置は見た目を変えるときに変わるので使わない。
- ページの変化は決まった秒数で待たない。`until` で変化した後の状態を待つ。
- browser の呼び出しが終了コード 0 で終わったときに機能ファイルの観測する結果と照らす。`ng` の行が出たら [mosidas.dev の検証の手引き](../README.md) の「2. 健康診断」を実行する。終了コード 2 で終わったら操作の書き方が誤っているので機能ファイルのとおりに書き直して実行し直す。`ng` の行を出さずに終了コード 1 で終わったときは出力が示す対処(`up を実行する` など)を行う。出力が対処を示さなければ出力を報告する。
- コマンドは書かれたとおりに実行する。引用符とセレクターを変えない。
- HTTP の要求は [mosidas.dev の検証の手引き](../README.md) の「3. 操作」にある curl のコマンドの型で送る。ヘッダー `Origin: https://mosidas.dev` を付ける。応答の本文は `-o` で `$EVIDENCE_DIR/<機能 ID>/` に保存する。機能 ID は機能ファイルの名前から `.md` を除いた語(`shell`・`pages`・`contact`)である。
- 後始末で証拠を削除しない。

## 証拠と省略の報告

- 利用者の操作とその結果の状態を取る。最後の画面だけでは足りない。
- 画面の証拠は `shot` のスクリーンショット(PNG)と `text` で保存した `innerText` の 2 つである。
- HTTP の証拠は curl の状態コードと応答の本文である。
- 副作用の証拠は `wrangler.log` の要求の行と Worker のログの行である。問い合わせの API(`/api/contact`)へ要求を送らない機能では `grep -a -c '\] [A-Z]* /api/' "$EVIDENCE_DIR/wrangler.log"` が 0 であることを証拠にする。要求の行は応答の後に遅れて書かれることがある。そのため、最後に送った要求の行が `wrangler.log` に出たことを確かめてから数える。
- 証拠は `$EVIDENCE_DIR/<機能 ID>/` に保存する。使った入口は `browser.log` の `open` の行に残る。
- 報告には証拠ごとにサブ機能の ID と使った入口を書く。
- 届かなかった経路は試したコマンドと満たせなかった前提を書いて報告する。
- 別の経路で通したことを届かなかった入口の合格として報告しない。

## 機能ファイルの形

各機能ファイルは H1 の題と利用者から見た振る舞いの 1 段落で始める。続けて次の 4 つの H2 を持つ。順は変えない。

1. `サブ機能`: 短い ID と 1 行の振る舞いを並べる。
2. `利用者からの到達`: 利用者の入口をすべて並べる。
3. `操作`: `前提:` で始める。利用者の操作・正確なコマンド・観測する結果を組にしたラベル付きの箇条を続ける。
4. `落とし穴`: 検証の時間を無駄にするか結果を無効にする罠を並べる。

実装の詳細を書かない。書くのは利用者の経路・安定した手掛かり・必要な状態・コマンド・観測できる証拠だけである。

- [ページの閲覧と移動](./pages.md): ヘッダーのナビ・制作物の一覧と詳細の前後・記事の一覧・プライバシーポリシー・無いページを扱う。
